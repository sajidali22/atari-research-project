What this file does. factory.py is an adapter. Six unrelated encoder architectures, each with its own constructor signature and its own way of producing a latent, are made to look identical to stable-baselines3. It exports exactly one function to the outside world, build_policy_kwargs(), and the training script calls nothing else.

1 What the file is for

Every architecture in the study has a different interface. A VAE exposes fc_mu. A VQ-VAE returns a tuple from its quantiser. The JEPA encoder wants a second argument that no other model takes. Left unmanaged, the PPO script would need a branch per architecture in the middle of the training loop.

   6 different encoder interfaces                 1 uniform interface
   ────────────────────────────                     ───────────────────
   StandardVAE      .fc_mu(...)          ┐
   EmaVqVae         .quantizer(...)      │
   AtariResidualVQVAE                    │   factory.py      forward(obs) -> [B, D]
   AtariFSQVAE      .fsq(.pre_quant...)  ├──▶  adapter   ──▶  .features_dim
   AdvancedViTVQVAE                      │                    nn.Module
   PaperAccurateJEPA(obs, env_vector)     ┘

The training script therefore contains no architecture-specific code at all. Swapping the representation is a change to one YAML field.

2 The contract stable-baselines3 imposes

To plug a network into SB3 you subclass BaseFeaturesExtractor. The base class is remarkably small. This is the whole thing:

  stable_baselines3/common/torch_layers.py
  class BaseFeaturesExtractor(nn.Module):
      def __init__(self, observation_space, features_dim=0):
          super().__init__()
          assert features_dim > 0
          self._observation_space = observation_space
          self._features_dim      = features_dim

      @property
      def features_dim(self): return self._features_dim

So the contract has three obligations, and that is all:

1. accept
observation_space as the first constructor argument. SB3 supplies it; you never pass it yourself.
2. declare
the output width, by calling super().__init__(space, dim). It must be known before the first forward pass, because SB3 sizes the policy and value heads from it.
3. implement
forward(obs) -> [B, features_dim]. A flat 2-D tensor.

The awkward one is obligation 2. SB3 needs the width at construction time, but for most of these encoders the width is a consequence of the architecture rather than something written down anywhere. The two extractor classes solve this differently, which is the single most interesting design detail in the file.

PretrainedExtractor — measure it

Runs one dummy batch of zeros through the encoder and reads the output shape. Works for any architecture without knowing anything about it.

dim = encode(backbone,
        torch.zeros(1, *obs_space.shape)).shape[1]

JepaExtractor — compute it

Reads the embedding width out of the checkpoint's saved config and multiplies by the token count. No forward pass needed.

36 * cfg["embed_dim"]
   = 36 * 256 = 9216
Why the probe runs under eval(). A shape probe should have no side effects, but for one architecture it does. EmaVqVae's quantiser revives unused codebook entries from whatever batch it sees while in training mode. Probing it with a single frame of zeros would corrupt the codebook before training even starts. Hence backbone.eval() on the line before the probe.

3 The registry pattern

Five of the six architectures differ only in two ways: how to construct them, and how to get a latent out. Those two things are captured as a pair of callables in one dictionary.

  ARCHS = {
      name          (  builder closure                    ,  encode function )
      "vae":       (_builder("models.standard_vae","StandardVAE"), _encode_vae),
      "ema_vqvae": (_builder(… num_embeddings=512, embedding_dim=64), _encode_vq),
      "vqvae":     (_builder(… num_embeddings=512, embedding_dim=64), _encode_vq),
      "fsq":       (_builder(… hidden_dim=128, fsq_levels=[8,5,5,3]), _encode_fsq),
      "vit_vqvae": (_builder(… num_embeddings=512, embed_dim=256),    _encode_vit_vq),
  }

_builder returns a closure rather than a model. Nothing is imported or constructed until that closure is called, so a run of the FSQ arm never imports the ViT module. That matters here because one of those modules is currently broken, and an eager import would take down every arm with it.

The encode functions are two lines each and exist because the bottleneck differs:

encode fnWhat it doesUsed by
_encode_vaetakes the posterior mean, never a sampleStandardVAE
_encode_vqencoder then quantiser, discards the second return valueEmaVqVae, AtariResidualVQVAE
_encode_fsqencoder, projection, then finite scalar quantiserAtariFSQVAE
_encode_vit_vqViT encoder, 1×1 compression, then quantiserAdvancedViTVQVAE

Taking the mean rather than a sample from the VAE is a deliberate choice worth defending. A stochastic extractor would make the features differ between the rollout and the update computed from that rollout, which silently violates an assumption PPO's importance ratio depends on.

Adding a seventh architecture is one dictionary entry plus, at most, a two-line encode function. The JEPA model is the one architecture that cannot fit this table, because it needs a second input, so it gets its own class instead.

                ╱        ╲

The middle class exists only so the freezing logic is written once. It defines no __init__, which is why both subclasses must call _set_frozen() themselves as the last step of their own constructor.

Four ordering constraints are load-bearing in that constructor, and three of them would produce confusing errors rather than clean ones if violated:

  • Path before import. Lines 136 to 138 must stay in that order.
  • super().__init__ before any self.x = module. PyTorch raises only a vague attribute error otherwise.
  • map_location="cpu". A checkpoint saved from a GPU otherwise tries to restore onto a specific device index that may not exist on the node it lands on. SB3 moves the finished policy to the right device afterwards.
  • _set_frozen last. It iterates self.parameters(), so anything assigned after it would be missed and would silently stay trainable.
The most dangerous line in the file is 145. The world model was trained under torch.compile, which prefixes every parameter name with _orig_mod.. Loading such a state dict without stripping that prefix matches nothing. With strict=False anywhere in the path, that failure is silent, and you get a randomly initialised encoder that still trains and still produces a plausible learning curve. PretrainedExtractor takes the same precaution at line 80 and additionally prints the missing and unexpected key counts.

7 A bug this timeline exposes

Confirmed: orthogonal init overwrites 75.7% of the pretrained encoder

SB3 applies orthogonal initialisation to self.features_extractor at step 5, which is after your constructor loaded the checkpoint at step 2. Its init_weights helper reinitialises every nn.Linear and nn.Conv2d it finds, recursively. ortho_init defaults to True and is not currently set in build_policy_kwargs.

Measured on a real build, Pong, frozen:

3,749,120 overwritten  (75.7%) 1,204,224 kept

The frozen run then trains a policy on top of a mostly random encoder, while printing every message that says the checkpoint loaded correctly.

The surviving half is arguably worse than none surviving. Attention input projections and layer norms are kept while the output projections and every feed-forward block around them are replaced with random matrices. The result is not the pretrained model and not a clean random baseline either.

The fix

  in build_policy_kwargs, for every pretrained arch:
  kwargs.update(
      ortho_init=False,
      features_extractor_class=JepaExtractor,
      ...
  )

Verified on the same build:

SettingEncoder params differing from the checkpoint
ortho_init=True  (current default) 3,749,120  of  4,953,344
ortho_init=False 0  of  4,953,344

The cost of the flag is that the policy and value heads lose orthogonal init too, falling back on PyTorch defaults. That is a mild and well-understood tradeoff. Keeping orthogonal init on the heads alone is possible, but needs the extractor's weights restored after construction rather than a single flag.

The baseline arm is unaffected. NatureCNN is supposed to be randomly initialised, so orthogonal init is correct there. The bug only touches arms that load pretrained weights, which is every arm the study is actually about. The same mechanism hits the VAE and VQ-VAE extractors, whose encoders are built from nn.Conv2d throughout.

8 Freezing, both halves

Freezing needs two mechanisms because SB3 actively fights the obvious one.

  def _set_frozen(self, frozen):
      self.frozen = frozen
      if frozen:
          for p in self.parameters():
              p.requires_grad = False      ◀ half 1: optimiser cannot update it
          self.eval()                      ◀ half 1.5: dropout off, for now

  def train(self, mode=True):
      return super().train(False if self.frozen else mode)
                            ◀ half 2: and it STAYS off

  every PPO iteration:

  collect_rollouts()   →  policy.set_training_mode(False)   on_policy_algorithm.py:184
  train()              →  policy.set_training_mode(True)    ppo.py:189
                              │
                              │  self.train(True) recurses into EVERY submodule
                              ▼
                          extractor.train(True)
                              │
                              ▼
                          overridden → super().train(False)   ← ignored

Without the override, two things move even though no gradient reaches them. Dropout switches back on, making the "frozen" features stochastic and inconsistent between the rollout and the update computed from it. And the EMA codebook in the VQ-VAE arms rewrites itself from whatever batch it sees whenever it is in training mode, which is a parameter update with no optimiser involved.

The startup print at train_sb3.py:196 is the check. For Pong the gap between the two modes should be exactly 4,953,344, the size of the encoder plus the embedding table.

--frozen9,441,79914,395,143

The frozen count is large because features are 9216-wide and net_arch=[512] as a list gives the policy and the value function a 512-unit trunk each, not one shared trunk. That is 2 × 9216 × 512 weights before the heads.

9 build_policy_kwargs, the only public function

  arch == "nature"            arch == "jepa"              everything else
        │                            │                           │
        ▼                            ▼                           ▼
  {net_arch:[512]}         JepaExtractor              PretrainedExtractor
  early return             + checkpoint               + arch name
                           + game                     + checkpoint
                           + env_mode                 + freeze

Two details in there are easy to miss and both are deliberate.

  • os.path.abspath(checkpoint). SB3 saves features_extractor_kwargs into the model zip. When train_sb3.py reloads the model for the final test evaluation, the extractor is reconstructed from those saved kwargs and the checkpoint is read again. A relative path recorded at save time would resolve against whatever directory the reloading process happens to be in.
  • dict(net_arch=list(net_arch)). Copying the list stops SB3 or a caller from mutating the module-level NET_ARCH default, which would leak into every later run in the same process.

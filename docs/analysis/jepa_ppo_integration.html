How train_sb3.py plugs in the JEPA model

PPO / universal  ·  every number on this page was read off a real build, not estimated

The one idea. The training script never builds, loads, or calls the JEPA model. It hands stable-baselines3 a recipe — a class and some arguments — and stable-baselines3 constructs the encoder itself, at the moment it builds the policy. That indirection is why one script runs the CNN baseline and the world model with no if statement anywhere in the training loop.

1 Where this sits in the project

Three stages, loosely coupled. This page is about the arrow between stage 2 and stage 3.

  STAGE 1                    STAGE 2                        STAGE 3

The checkpoint file is the entire interface between the two halves of the project. Stage 3 knows nothing about how the world model was trained. It only needs the file.

2 The plug-in mechanism

Stable-baselines3 lets you replace the vision network inside its policy. You pass a dictionary called policy_kwargs. Two keys matter:

features_extractor_class
a class, not an instance. Stable-baselines3 will call it for you.
features_extractor_kwargs
the arguments to pass when it does. Everything except observation_space, which stable-baselines3 supplies on its own.

So the whole integration is: build that dictionary correctly, then get out of the way. build_policy_kwargs() at the bottom of factory.py is the only function that does it.

Why "CnnPolicy" is still correct. It looks wrong to ask for a CNN policy and then hand over a Vision Transformer. But "CnnPolicy" only tells stable-baselines3 that observations are images. Its default vision network is NatureCNN, and features_extractor_class overrides that default. The string is about the observation type, not the architecture.

3 What actually gets loaded

The checkpoint holds the whole world model, including parts that only exist to make training work. The extractor keeps two of the five pieces.

Piece in the checkpointParamsWhy
context_encoder4,949,248 kept This is the representation. Frames go in, features come out.
env_embed4,096 kept 16 × 256 lookup table. Tells the encoder which game it is looking at.
target_encoder4,949,248 dropped A slow-moving copy of the context encoder. It exists to stop the world model from collapsing during pretraining. Useless once pretraining is over.
predictor2,374,400 dropped Predicts the next latent state given an action. That is the world-modelling task itself. PPO learns its own policy, so it is not needed.
inverse_head201,490 dropped Auxiliary inverse-dynamics head, a pretraining-only signal.

Out of 12,478,482 saved parameters, 4,953,344 are carried into the RL run and the rest are discarded at load time. Discarding happens by simply not keeping a reference: factory.py:146-147 pulls out two attributes and lets Python garbage-collect the rest of the model object.

  ckpt = torch.load(checkpoint)
  cfg  = ckpt["model_config"]              ◀── architecture is read FROM the file,
                                               not hardcoded. weights and shape
  model = PaperAccurateJEPA(**cfg)             can never drift apart.
  model.load_state_dict(strip_compile_prefix(ckpt["model_state_dict"]))

  self.encoder   = model.context_encoder    ◀── keep
  self.env_embed = model.env_embed          ◀── keep
                         target_encoder     ◀── no reference taken, freed
                         predictor
                         inverse_head
The _orig_mod. problem. The world model was trained under torch.compile, which silently renames every parameter with an _orig_mod. prefix. Loading such a state dict into an uncompiled model matches nothing and, with strict=False, fails silently into a randomly initialised encoder. strip_compile_prefix removes the prefix. This is the single most dangerous failure mode in the whole pipeline, because the run still trains and still produces a curve.

The number 36 is fixed by geometry: 84 divided by a patch size of 14 gives a 6×6 grid. The number 9216 is 36 × 256 and is computed at factory.py:142 rather than hardcoded, so a checkpoint with a different embedding width still works.

The frames are normalised exactly once. Stable-baselines3 divides by 255 before the extractor runs. The JEPA encoder also calls a to_float helper, but that helper passes floats through untouched and only rescales uint8. Both halves were written to normalise, and it still works, because one of them checks first.

5 Telling the encoder which game it is looking at

This is the part that has no equivalent in the CNN baseline. The encoder takes a second input besides pixels: a 256-dimensional vector identifying the game. There are 16 slots.

0BeamRider 1Breakout 2DemonAttack 3Enduro 4MsPacman 5Pong 6Qbert 7Riverraid 8RoadRunner 9Seaquest 10SpaceInvaders 11UNKNOWN 12Alien 13Asteroids 14Atlantis 15IceHockey

Green: trained on. Amber: the generic slot. Grey: reserved for held-out games, allocated but never given a gradient during pretraining.

Which slot gets used is decided by one line, factory.py:149:

  slot = gamelib.UNKNOWN_ID if env_mode == "unknown" else gamelib.GAME_TO_ID[game]
  self.register_buffer("env_slot", torch.tensor(slot))

Two things worth pointing out to a reviewer:

  • It is a buffer, not a plain tensor. Registering it means .to("cuda") moves it along with the weights. A plain attribute would stay on the CPU and crash on the first forward pass.
  • --env-mode unknown is the zero-shot experiment. Point it at a game the world model never saw, and slot 11 supplies a generic "some Atari game" vector instead of a game-specific one. The encoder runs unchanged. Without this slot there would be no defined input for an unseen game at all.
A YAML trap that is already handled. In configs/jepa.yaml the value is written env_mode: "true" with quotes. Unquoted, YAML parses true as a boolean, the string comparison env_mode == "unknown" still works, but the argparse choices check rejects it and the run dies at startup.

6 What "frozen" really means

Freezing the encoder takes two separate mechanisms, and the obvious one alone is not enough.

Part 1 — no gradients

requires_grad = False on every parameter. The optimiser cannot update the encoder. This part is obvious and most people stop here.

Part 2 — pinned to eval mode

Stable-baselines3 calls policy.set_training_mode(True) before every update, which propagates into the extractor. So train() is overridden to ignore it while frozen.

  factory.py:99
  def train(self, mode=True):
      return super().train(False if self.frozen else mode)
                            ▲
                            └─ SB3 asks for train mode every update; we say no

Without part 2, two things would drift even with zero gradients:

  • Dropout switches back on inside the transformer, so the "frozen" features become stochastic and differ between the rollout and the update that follows it.
  • The EMA codebook in the VQ-VAE arms rewrites itself from whatever batch it sees whenever it is in train mode. No gradient is involved. The representation would quietly change under the RL objective, which destroys the experiment's premise.

The check that proves it worked

train_sb3.py:196 prints the trainable parameter count at startup. These are the real numbers for Pong:

RunTrainableTotalWhat is learning
--frozen9,441,79914,395,143 policy and value trunks only
--joint14,395,14314,395,143 everything, encoder included

The gap is exactly 4,953,344, which is the encoder plus the embedding table from the table in section 3. If those two numbers are equal in a frozen run, the freeze silently failed.

Worth knowing: the trainable count is large even when frozen, because the features are 9216-wide and stable-baselines3 builds a separate 512-unit trunk for the policy and for the value function. That is 2 × 9216 × 512 weights in the heads alone.

Setting net_arch explicitly matters more than it looks. Left alone, stable-baselines3 defaults to an empty head for its own NatureCNN and a [64, 64] head for a custom extractor. The two arms would then differ in head capacity as well as in representation, and any result would be uninterpretable.

8 Three environment splits

Not part of the JEPA plumbing, but a reviewer will ask, and it is the reason the reported numbers are trustworthy.

SplitSeedRewardsUsed for
trainseedclipped, ends on life loss the PPO updates
validationseed + 10,000raw, full episode selecting best_model.zip
testseed + 20,000raw, full episode the final reported score, once

Training uses clipped rewards because PPO needs a bounded signal. Validation and test disable clipping and life-loss termination, so their numbers are true game scores that can be compared against published Atari results. The test split never influences training or model selection, which is what makes the final number honest.

Both the final and the best checkpoint are evaluated and both are written to test_results.json. Reporting only the best would be quietly selecting on validation noise.

9 Questions a reviewer is likely to ask

Is the encoder genuinely frozen, or just not receiving gradients?
Genuinely frozen. Gradients are off and eval mode is pinned, so dropout and any EMA state cannot move either. The startup parameter count is the evidence.

Are the pixels normalised twice?
No. Stable-baselines3 divides by 255, and the encoder's converter only touches uint8 tensors, so it is a no-op on the already-scaled input.

How do you know the pretrained weights actually loaded?
The compile-prefix strip runs before loading, and any missing or unexpected keys are printed. A silent fallback to random weights is the failure this guards against.

Why is a Vision Transformer being loaded by something called CnnPolicy?
That string selects the image-observation policy, not the architecture. The architecture comes from features_extractor_class.

Is the comparison against the baseline fair?
Same PPO implementation, same hyperparameters from the same YAML structure, same [512] head, same three env splits, same seeds. The extractor is the only thing that differs.
